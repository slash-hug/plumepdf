# Fixtures — provenance

Per the clean-room policy in AGENTS.md: **every
file in this directory is self-authored**, generated by the committed
`generate_fixtures.py` script rather than sourced from any third-party PDF,
test suite, or corpus. Nothing here was copied, extracted, or derived from
iText7, Aspose, Syncfusion, QuestPDF, or any other PDF library or PDF file
found on the internet.

`generate_fixtures.py` builds every file from first principles: the PDF
object/xref/stream framing is written directly from ISO 32000-1 (an approach the
clean-room policy in AGENTS.md allows), and the AES block cipher is implemented directly
from FIPS-197 (the public NIST standard) with its own self-check against the
standard's published test vectors. `validate_fixtures.py` then independently
re-parses every fixture (and, for the encrypted ones, re-derives the file key
and decrypts the content stream) to prove each file is internally consistent
before it's trusted as a test input.

Regenerate everything with:

```sh
cd tests/PlumePdf.CorpusTests/Fixtures
python3 generate_fixtures.py     # writes all *.pdf, deterministically
python3 validate_fixtures.py     # independently re-checks every one
```

Both scripts use only the Python standard library (`zlib`, `hashlib`,
`struct`) — no third-party package, and in particular no PDF library, is
ever imported.

## Files

Every fixture is a minimal one-page "Hello, PlumePDF fixture" document
(Helvetica text on a 200×100 MediaBox); only the framing named below differs.
All are self-authored; provenance is identical for every row and is not
repeated per-file below.

| File | Exercises |
|---|---|
| `classic-xref.pdf` | A plain classic cross-reference table (ISO 32000-1 §7.5.4) — the baseline shape. |
| `xref-stream.pdf` | A PDF 1.5+ cross-reference **stream** (§7.5.8), Flate-compressed with a PNG "Up" predictor (§7.4.4.4, `/Predictor 12`) — the shape that makes Filters a dependency of parsing Objects at all. |
| `object-stream.pdf` | Three objects (Catalog, Pages, Font) packed into a compressed `/ObjStm` (§7.5.7), indexed by a compressed xref stream with type-2 entries; the Page and content-stream objects stay uncompressed (streams can't live inside an object stream), exercising the mixed-resolution path. |
| `hybrid.pdf` | A hybrid-reference file (§7.5.8.4): a classic xref table for the visible document, plus a trailer `/XRefStm` pointing at a supplemental xref stream that resolves one extra object stored in an `/ObjStm` — old readers see the base document, new readers see everything. The classic table here simply omits the compressed object's number. |
| `hybrid-freemarked.pdf` | The real-world hybrid shape `hybrid.pdf` doesn't cover: the classic table lists **every** object number, including the one that only really lives in the `/XRefStm`-referenced object stream — marked *free*, the shape Acrobat and most producers emit — rather than omitting it. Exercises `/XRefStm` override precedence over a same-revision classic Free entry (`CrossReferenceTests`). |
| `linearized-ish.pdf` | Carries a first-object linearization parameter dictionary (Annex F: `/Linearized 1 /L /H /O /E /N /T`) so header-recognition code has something to see, **without** implementing true linearization's first-page xref section and hint stream — hence "-ish". Underneath it is an entirely ordinary, valid, classic-xref document. |
| `broken-xref.pdf` | A structurally well-formed classic xref table whose offsets are all deliberately wrong; every object is still present and findable by a brute-force `N G obj` scan — the recovery ladder's "repairable deviation" rung. |
| `truncated.pdf` | A file cut off mid-write: every object is intact, but the xref table, trailer, `startxref`, and `%%EOF` are all missing entirely — an interrupted upload/download. |
| `RC4-40.pdf` | Standard Security Handler, `/V 1 /R 2`, 40-bit RC4, empty user **and** empty owner password (the common "encrypted but not password-protected" shape). |
| `RC4-128.pdf` | `/V 2 /R 3`, 128-bit RC4, empty user/owner password. |
| `AES-128.pdf` | `/V 4 /R 4`, AESV2 crypt filter (AES-128-CBC, per-object key via Algorithm 1 + `"sAlT"`), empty user/owner password. |
| `AES-256.pdf` | `/V 5 /R 6`, AESV3 crypt filter (AES-256-CBC), key derivation via the ISO 32000-2 §7.6.4.3 hardened-hash algorithm, empty user/owner password. |

## Known simplifications

- **`linearized-ish.pdf`** is not a conformant linearized file (no real
  first-page xref section or hint stream) — it only carries the
  linearization parameter dictionary as object 1, by design (see table
  above).
- **`AES-256.pdf`** omits the optional `/Perms` entry (an Acrobat-only
  owner-permission integrity check that isn't required to derive the file
  key or decrypt content) — out of scope for Phase 1's encryption-**read**
  goal.
- All encrypted fixtures use `/P -4` ("all permissions granted") — Phase 1
  scope is encryption read, not permission enforcement, so any consistent
  value works; enforcement is not exercised by these fixtures.
- Every fixture uses a fixed document `/ID` and (for the encrypted ones)
  fixed salts/IVs derived deterministically from the filename, so
  regeneration is byte-for-byte reproducible. This is a test-fixture
  convenience, not a statement about how PlumePDF's own writer should pick
  IDs/IVs (see `PdfOptions.Deterministic` for that).

## Independent verification

Every fixture was additionally opened once in an independent, unrelated PDF
implementation ([Poppler](https://poppler.freedesktop.org/), via `pdfinfo`
and `pdftotext`) — a real "reference viewer" check that doesn't rely on our
own generation code at all:

- `classic-xref.pdf`, `xref-stream.pdf`, `object-stream.pdf`, `hybrid.pdf`
  all report `Pages: 1` with no errors, and `pdftotext` extracts "Hello,
  PlumePDF fixture" from each; `classic-xref.pdf` was additionally rendered
  to a PNG (`pdftoppm`) and inspected visually.
- `linearized-ish.pdf` opens correctly (`Optimized: yes`); Poppler emits the
  expected warnings about the placeholder `/H`/hint-table fields (documented
  above as a known simplification) but still reads the real trailer/xref
  and extracts the correct text.
- `broken-xref.pdf` triggers Poppler's own "xref num N not found, try to
  reconstruct" recovery path and still successfully extracts the correct
  text — direct confirmation that the object bytes are intact and
  independently recoverable, not just self-consistent with our own scan.
- `truncated.pdf` is **not** recoverable by Poppler or pypdf (both require
  at least a trailing `%%EOF`/xref keyword before attempting reconstruction)
  — this is expected and is exactly the gap PlumePDF's own brute-force
  recovery rung exists to cover; the fixture's correctness was instead
  confirmed structurally (all 5 `N 0 obj` markers present and byte-identical
  to the un-truncated file, via `validate_fixtures.py`).
- `RC4-40.pdf`, `RC4-128.pdf`, `AES-128.pdf`, `AES-256.pdf` all report
  `Encrypted: yes` with the correct algorithm name, open with the empty
  password automatically, and `pdftotext` extracts the correct plaintext
  from each — independent, real-world confirmation that the hand-rolled key
  derivation and cipher implementations in `generate_fixtures.py` are
  byte-correct, including the AES-256 revision-6 hardened-hash algorithm.

`validate_fixtures.py` covers the same ground without an external
dependency (pure re-parse + re-derive + decrypt, per file above).

  (`qpdf --encrypt … 256/128 --`), user password `user pass`, owner password
  `owner pass` (empty user password for the `-empty-user` variant). These are
  *externally produced* ground truth for the encryption-read paths — including
  the AES-256/R6 hardened-hash derivation, which `GroundTruthEncryptionTests`
  validates against them (closing the gap where R6 had only ever been checked
  against PlumePDF's own round-trip).

Provenance: all five derive solely from the self-authored `classic-xref.pdf`
